# Hermes Canary Action — Threat Model

## What the action reads

- Environment variables explicitly passed as inputs (`SENTRY_DSN`, `HERMES_API_KEY`, `HERMES_LICENSE_KEY`, `DD_API_KEY`, `DD_APP_KEY`, `PREVIOUS_RECEIPT_PATH`)
- `GITHUB_REPOSITORY`, `GITHUB_SHA`, `GITHUB_EVENT_NAME`, `GITHUB_EVENT_PATH` (standard GitHub context)
- `GITHUB_TOKEN` (only when posting PR comments)
- The previous receipt JSON file at `PREVIOUS_RECEIPT_PATH` (if provided)

## What leaves the runner

| Scenario | Destination | Data sent |
|---|---|---|
| Free tier, no DSN | Nothing | Nothing |
| Sentry DSN provided | Customer's Sentry endpoint | Scrubbed probe message (no raw canary token) |
| Pro tier, API key provided | api.hermesrelay.dev | Signed receipt JSON (no canary payloads) |
| Pro tier, Datadog keys provided | Customer's Datadog account | Synthetic log events with canary tokens |
| PR comment | api.github.com | Markdown summary of test results |

## What the signature provides

HMAC-SHA256 proves that the receipt was generated by a party holding the Hermes API key and that the receipt content has not been altered since signing. It does not prove that the canary test was run on the stated commit or that the runner was uncompromised.

## What it doesn't provide

- It does not guarantee that all PHI-scrubbing edge cases are covered. The canary tests only the 16 HIPAA Safe Harbor categories against synthetic fixed patterns.
- It does not replace a full penetration test or code audit of your application's telemetry integration.
- It is not a business associate agreement (BAA). Hermes does not process PHI.
- It is not HIPAA certification or a SOC 2 audit of this action.

## Assumptions

- The GitHub Actions runner is trusted (standard GitHub security model applies).
- The customer's `SENTRY_DSN`, `HERMES_API_KEY`, and Datadog keys are stored as GitHub encrypted secrets.
- The customer has not modified the action's source after SHA-pinning.
